# CSV deliverable validation

Cloud tasks validate CSV output before accepting `done`. CSV syntax and uniform column counts are independent checks: a report can have equal-width rows and still have invalid quotes.

Pi offers `write_csv` with structured headers and rows, which escapes commas, quotes, empty cells and multiline values, validates the result, and writes atomically. A task can also use Python's `csv.writer` or another correct CSV writer. Output paths belong in both the user-facing result and the optional `csvOutputs` envelope array. Existing outputs returned from a resumed session must be declared there as well.

Validation covers files written by `write_csv`, newly created/modified CSV files in the task root, and newly created/modified nested CSV files named in the result. Explicit `csvOutputs` are checked even when unchanged. This keeps read-only input analysis separate from delivery: an unchanged malformed input is not silently rewritten merely because the answer discusses it. Hidden runtime files and dependency/cache trees are excluded. Files must be UTF-8, task-local regular files, at most 25 MiB; symlink escapes are rejected. Parsing uses strict quotes, fixed column counts, BOM support and blank-record skipping. A file must have a header; header-only tables are allowed. This validates format, not factual accuracy or fulfillment of every requested research source.

For Pi, a failed check allows one bounded format-repair request, at most 30 seconds, with only `write_csv` enabled. The native task is not replayed, browsing and commands are disabled, and the original decision's schedules/memories/page actions cannot be extended by the repair response. Only reported invalid files may change. A repair may change quoting/BOM and normalize line endings; other text, commas and record order must remain identical. Original invalid text is backed up privately in `.coke-dots-agent-runtime/csv-originals`. Repairs are limited to three files and 18,000 characters total. Unreadable/oversized/unsafe or still-invalid output prevents `done` and preserves evidence.

The repair yields after one complete tool batch and does not launch another summary or final model reply. It does not change normal task compaction behavior or extend the task execution limit (currently 20 minutes). DSH has the same completion validation, without Pi's tool-repair mechanism. Partial/failed-task artifacts remain downloadable for inspection; the download route is not changed into a repair operation. Historical user files and task states are not bulk rewritten.

Regression coverage includes malformed thousands separators, equal-width invalid quotes, multiline/BOM round trips, read-only inputs, original-file preservation, tenant/task path boundaries, data-changing or non-CSV repair attempts, one-time shell side effects, and repair above the soft context budget without compaction or replay.
