# Pi 结果协议与 Browser Use / Computer Use 核查

核查时间：2026-10-18。对象是 `dot.cugxuan.cn` 的 Linux Docker 部署；独立的 Mac `/dots-demo/` 未纳入此次核查。

## 正常文字回复被判失败

失败任务 `3b8150ef-795c-435f-a463-60e63b83876a` 的原生 Pi 日志显示：`deepseek-v4-flash-ga-260731` 以 `stop` 正常结束，输出“V4-Flash 配置验证成功。”，没有调用工具。应用要求 JSON 决策，但要求与用户的“只回复这句话”一起放在 user 消息中；解析器因此抛出 `Agent did not return a structured result`。

修复把应用的结果协议追加到 Pi 的系统指令：用户只看到 `message`，JSON 是应用内部包装，不属于工具操作或用户文件。普通有效结果仍只需要一次模型调用。遇到非空但格式不正确的最终答案，只在原生会话内执行一次格式整理：禁用所有工具及自动重试，最多一次整理请求、30 秒期限。保留先前工具证据，禁止重跑任务。等待用户、定时检查和委派状态保留原语义；接口失败、空回复、截断和取消继续报错。整理仍失败时保留会话并明确报告，避免无限重试。

真实 Pi SDK + 模拟 HTTP 模型的回归验证了系统消息、纯文字修复、状态/可选字段保留、Bash 副作用只执行一次、原生会话续接、禁止整理时调用工具、取消及接口错误。全套单元测试 225 项：221 通过，4 项 macOS 条件跳过；类型检查和服务端构建通过。当前真实 Flash 接口的三次不同精确回复均成功，均一轮模型、零工具；本机适配器耗时约 1.24–2.04 秒，不能等同于完整公网请求耗时。

## Browser Use：已有正确的执行入口

当前路径是 `任务 → 租户 Pi → browser_execute → Browser Use Pi / Playwright → 租户 Chromium CDP`。Pi 负责唯一的模型决策循环，Browser Use 负责执行代码、管理标签页及保存操作证据。现有接入没有启动第二个浏览器 Agent。

- 使用官方组织的 [Browser Use Pi](https://github.com/browser-use/browser-use-pi)，固定上游提交 `e73c28b87998afddc168951b3f768a3f0e81d640`，来源及许可证见 `vendor/README.md`。
- 仅使用 `BrowserUse.create/execute/close`，不调用 `run/followUp`；与用户看到的租户浏览器共用已有标签页和登录状态。
- DOM/无障碍树提供观测到的元素 ID，Playwright 执行点击、输入和条件等待；已知的连续操作可以批量执行，每次调用后返回新页面状态。
- 用户接管会取消活动执行；恢复时重新观察页面。结束任务保留标签页与登录。真实 Chromium 回归覆盖批量操作、超时、失效 ID、关闭标签、保留登录及接管取消。

用户提到的 [browser-use/browser-use](https://github.com/browser-use/browser-use) 是同一组织的完整浏览器 Agent 项目，提供 Python 库等入口。它不是控制浏览器的唯一方式。对当前 TypeScript + Pi 架构，继续使用已有执行器更合适；再套一个完整 `Agent.run()` 会引入第二套模型循环、状态、用量统计和取消机制。若未来改用 Python 版本，应替换执行边界并实测收益。

## Computer Use：基础设施与 Agent 能力有缺口

Worker 已有桌面截图及 `xdotool` 的点击、输入和有限按键接口；用户接管使用 noVNC。**这些基础设施不代表 Pi 已具备完整的桌面 Computer Use 工具。** 当前注册的 `computer_browser` 仍是浏览器元素操作工具，没有向模型提供统一的桌面截图、坐标点击、滚动、拖拽等动作协议。Bash 可以间接操作桌面，但缺少专用工具的约束和观测流程。

[Computer Use 的官方工具说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)将其定义为截图、鼠标和键盘驱动的桌面交互。网页内任务应优先走已有的浏览器元素路径；操作系统窗口、原生对话框及无法用 DOM 访问的画面，才需要桌面视觉路径。

另一个实际问题是视觉模型能力。`model-policy.mjs` 当前按整个 Ark `deepseek-v4` 家族声明图片输入，这个推断过宽。对当前精确型号 `deepseek-v4-flash-ga-260731` 的直接接口检查中，64×64 红色 PNG 被回答为“白色”；进一步用经解码验证的 640×480 红、绿、蓝三张 PNG，接口均 HTTP 200，但都回答“无法看图”。因此本次检查没有验证该部署的有效图像理解能力，更不能据此宣称它能可靠进行截图定位。这个结论不适用于其他 Flash 别名、视觉版本或 V4.1；也不是一次完整的视觉基准。本次未更改共享模型设置。

## 后续方案与验收边界

1. 常规网页继续使用 Browser Use 的 DOM/CDP 路径。把每轮耗时分成模型、工具、网页等待，减少无意义的“看一眼再调用一次模型”，保持条件等待与批量动作。
2. 按具体模型/部署验证并声明视觉能力；不要由家族名称直接推断。选择能通过截图读取和坐标定位验证的视觉模型，再增加专用 Computer Use 工具。
3. 新桌面工具与浏览器工具共用同一租户、任务、取消信号和控制权。截图携带尺寸/缩放与观测版本；动作校验边界，支持滚动、拖拽、组合键，执行后重新截图。用户接管必须停止后续动作。
4. 用真实桌面流程验收：原生窗口、非 DOM 画面、坐标缩放、接管中断/恢复、错误后的副作用保留及跨租户隔离。先通过这些测试，再向 UI 暴露完整桌面自动控制能力。

目前 Agent 模式下的画面仍每两秒刷新，接管后切 noVNC。这会影响观看的即时感，但不是模型每步停顿很久的同一个原因；此前排除的 P2 画面推送优化保持待办。本次交付修复结果协议并核查两类控制方案，没有新增桌面视觉 Agent。
